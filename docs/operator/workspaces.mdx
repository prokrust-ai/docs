A workspace is a Kubernetes namespace assigned to one Prokrust installation. Enroll a namespace before users create tables in it.

## Before you begin

- Install the `prokrust-crds` chart once in the cluster. Enable the definition for each connection type your users need.
- Install `prokrust-system` in a dedicated system namespace. Enable the provider controller and registry entry for each connector you plan to use.
- Choose a separate namespace for the workspace. Use a `prokrust-workspace` chart whose `supportedSystemVersion` matches the installed system release. The workspace and system charts have separate version numbers.
- Prepare your workspace values file. It supplies cluster-specific settings, such as worker storage, workload identities, and image pull credentials. See the [workspace chart values](https://github.com/prokrust-ai/helm-charts/blob/main/charts/prokrust-workspace/values.yaml).

## Enroll the namespace

Use the tool that owns the workspace release. For Argo CD, you need an existing Application with the chart, version, values, and destination namespace. Its sync must be able to create the namespace if needed. For Helm, use a Kubernetes context with permission to install the workspace chart.

<ActionTabs>
<TabItem value="ui">

1. In **Argo CD → Applications**, open the workspace Application.
2. Check its destination namespace and chart version against the workspace you prepared.
3. Select **Sync**. Select **Synchronize** for the full Application so its enrollment hook runs.

</TabItem>
<TabItem value="k8s">

Set the three shell variables below before you run Helm.

```bash
helm install prokrust-workspace oci://ar.prokrust.io/charts/prokrust-workspace \
  --version "$WORKSPACE_CHART_VERSION" --namespace "$WORKSPACE" --create-namespace \
  --values workspace-values.yaml --set-string installation.namespace="$SYSTEM_NAMESPACE"
```

| Input | How to choose it |
| --- | --- |
| `WORKSPACE_CHART_VERSION` | Use the compatible workspace chart release you selected. This pins the package Helm installs. |
| `WORKSPACE` | Use the workload namespace. `--create-namespace` lets Helm create it on the first install. |
| `workspace-values.yaml` | Use the path to the values file for this workspace. |
| `installation.namespace` and `SYSTEM_NAMESPACE` | Use the namespace of the installed `prokrust-system` release. The enrollment hook assigns the workspace to that installation. |
| `prokrust-workspace` | The first argument is the Helm release name. Use your release name if your deployment uses another one. The OCI URL selects the workspace chart. |

</TabItem>
<TabItem value="curl">

Send a sync request to Argo CD.

```bash
curl --fail-with-body -H "Authorization: Bearer $ARGOCD_TOKEN" \
  -H 'Content-Type: application/json' --data '{}' \
  "$ARGOCD_URL/api/v1/applications/$WORKSPACE_APP/sync"
```

- Set `ARGOCD_URL` to your Argo CD HTTPS origin. Set `WORKSPACE_APP` to the Application name in the Argo CD control namespace.
- Set `ARGOCD_TOKEN` to an Argo CD bearer token with sync permission for that Application.
- `Content-Type` identifies the JSON request body. The empty object uses the Application's configured revision and starts a full sync. A successful response acknowledges the request. [Argo CD API documentation](https://argo-cd.readthedocs.io/en/stable/developer-guide/api-docs/)

</TabItem>
</ActionTabs>

After Helm installs the chart or Argo CD finishes the sync, check the namespace's enrollment state.

## Verify enrollment

For a terminal command, set `WORKSPACE` to the namespace you enrolled.

<ActionTabs>
<TabItem value="ui">

In your Kubernetes web console, open the workload Namespace. Inspect its YAML.

</TabItem>
<TabItem value="k8s">

```bash
kubectl get namespace "$WORKSPACE" -o yaml
```

</TabItem>
<TabItem value="curl">

Start `kubectl proxy --port=8001` in a separate terminal with your administrator context. Read the Namespace through that local Kubernetes API proxy.

```bash
curl --fail --silent --show-error "http://127.0.0.1:8001/api/v1/namespaces/$WORKSPACE"
```

Port `8001` selects the local proxy. If you choose another port, use it in both commands.

</TabItem>
</ActionTabs>

Check these fields under `metadata`. The enrollment hook sets the installation label. The controller writes the enrollment annotations.

| Field | Expected value and purpose |
| --- | --- |
| `labels["prokrust.ai/installation"]` | The system namespace you selected. This label requests membership in that installation. |
| `annotations["prokrust.ai/enrollment-installation"]` | The same system namespace. This identifies the installation that processed enrollment. |
| `annotations["prokrust.ai/enrollment-uid"]` | The value of this Namespace's `uid`. Kubernetes assigns a new UID if someone deletes and recreates the namespace. |
| `annotations["prokrust.ai/enrollment-phase"]` | `Ready`. A new workspace can show `Pending` while the controllers check access and synchronize. |

If the label is missing, inspect the enrollment Job in the system namespace. If the phase stays `Pending`, check the controllers' access to the workspace.

## Verify the resource definitions

Kubernetes must serve both the `Table` kind and the connection kind. Set `CONNECTION_CRD` to the full name of the connection definition when you use a terminal. For S3, use `s3connections.aws.sources.prokrust.ai`. For the synthetic quickstart, use `syntheticconnections.sources.prokrust.ai`. [Kubernetes resource reference](/reference/#kubernetes-resources)

<ActionTabs>
<TabItem value="ui">

In your Kubernetes web console, open **CustomResourceDefinitions**. Inspect `tables.data.prokrust.ai` and the definition for your connection type.

</TabItem>
<TabItem value="k8s">

```bash
kubectl wait --for=condition=Established --timeout=30s \
  crd/tables.data.prokrust.ai "crd/$CONNECTION_CRD"
```

The command waits up to 30 seconds for both CRDs. Increase the timeout if the cluster has just installed them.

</TabItem>
<TabItem value="curl">

Use a local Kubernetes API proxy on port 8001 with your administrator context. Start it with `kubectl proxy --port=8001` if needed. The following command requires `jq`.

```bash
for crd in tables.data.prokrust.ai "$CONNECTION_CRD"; do
  curl --fail --silent --show-error \
    "http://127.0.0.1:8001/apis/apiextensions.k8s.io/v1/customresourcedefinitions/$crd" |
    jq -r '.metadata.name + " " + (.status.conditions[] | select(.type == "Established").status)'
done
```

The loop reads the two CRDs by name. In the response, `metadata.name` identifies each CRD.

</TabItem>
</ActionTabs>

For each CRD, find the entry under `status.conditions` whose `type` is `Established`. Its `status` must be `True`. The Kubernetes command reports when that condition is met. This check confirms that Kubernetes serves each kind. Check the connector controller separately if connections of that kind fail.

## Check table permissions

Check access with the workspace user's Kubernetes context. Set `WORKSPACE` to the enrolled namespace. Use Kubernetes or curl for this check. The Prokrust app has no Kubernetes access-review screen.

<ActionTabs>
<TabItem value="k8s">

```bash
kubectl auth can-i create tables.data.prokrust.ai -n "$WORKSPACE"
kubectl auth can-i get tables.data.prokrust.ai -n "$WORKSPACE"
```

The first command checks permission to register a table. The second checks permission to read its definition. Both use the current identity and the specified namespace.

</TabItem>
<TabItem value="curl">

Start `kubectl proxy --port=8002` with the **workspace user's context** in a separate terminal. The separate port keeps this request on the user's proxy. Use `jq` to send one access review per verb.

```bash
for verb in create get; do
  jq -n --arg ns "$WORKSPACE" --arg verb "$verb" \
    '{apiVersion:"authorization.k8s.io/v1",kind:"SelfSubjectAccessReview",
      spec:{resourceAttributes:{namespace:$ns,verb:$verb,group:"data.prokrust.ai",resource:"tables"}}}' |
    curl --fail --silent --show-error -H 'Content-Type: application/json' --data-binary @- \
      http://127.0.0.1:8002/apis/authorization.k8s.io/v1/selfsubjectaccessreviews |
    jq '.status.allowed'
done
```

| Review field | What it tests |
| --- | --- |
| `apiVersion`, `kind` | The Kubernetes authorization API requires `authorization.k8s.io/v1` and `SelfSubjectAccessReview` at this endpoint. This review tests the caller's own identity. |
| `spec.resourceAttributes` | Describes one action on a Kubernetes resource. Each loop iteration asks about a different action. |
| `spec.resourceAttributes.namespace` | Scopes the check to `WORKSPACE`. Change it to test access in another workspace. |
| `spec.resourceAttributes.group`, `spec.resourceAttributes.resource` | Together, `data.prokrust.ai` and `tables` identify the table resource. Use the connector's group and plural resource name to check connection access. |
| `spec.resourceAttributes.verb` | `create` tests registration. `get` tests retrieval of a definition. |
| `status.allowed` | The authorization result returned by Kubernetes. `true` permits the requested action. |

</TabItem>
</ActionTabs>

Expect `yes` or `true` for each verb. Give the user the workspace namespace, installation URL, and connection type and name. They can now [create a table](/user/create-a-table/). For the [synthetic quickstart](/user/synthetic-table/), also check permission to create synthetic connections.
